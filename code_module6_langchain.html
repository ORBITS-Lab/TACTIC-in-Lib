Why Agentic AI & LangChain?

In Module 5, librarians fine-tuned a model that does one job well and previewed agentic automation with Amazon Q. In this module the relationship flips. Instead of calling a model inside a pipeline you wrote, you build a system in which the model decides what to do next: which tool to call, what to search for, and when to stop.

Module Goal

Learners build a library reference agent with LangChain that calls tools, searches real scholarly data, and operates under privacy, approval, and citation guardrails. They then compare these runtime guardrails with training-time alignment (RLHF / DPO) to understand what a library can and cannot control.

LLM-based Application vs. LLM-based Agent

CategoryLLM-based ApplicationLLM-based Agent
DefinitionAn LLM integrated into a system built for one specific purposeA dynamic system where the LLM reasons and acts on its own
Control flowFixed pipeline: Input → LLM → OutputIterative loop: Reason → Select tool → Act → Observe → Repeat
Decision makerThe developer, through codeThe LLM, at each step
FlexibilityPredefined behaviorAdaptive, context-aware behavior
Library examplesTicket classifier (Module 5), summarizer, retrieval QAResearch assistant that searches, verifies, and cites

The agent execution loop

An agent is not a smarter model. It is the same model placed inside a loop with access to tools:

Goal→Plan→Act→Observe→Reflect→Repeat or finish

Your job shifts from scripting every step to supervising a process. That shift is what this module is really teaching.

Why LangChain?

LLMs become far more useful when combined with external data, tools, and application logic. LangChain makes it easy to start building such applications while still supporting production use. Three properties matter most here:

Abstraction

Express complex LLM tasks with reusable components such as @tool and create_agent.

Standardization

Swap Groq, Gemini, or a local model through one common interface.

Chaining

Connect models, tools, and middleware into a single working pipeline.

The Agent-Building Workflow

This module follows a 6-step path from a bare language model to a library agent you could responsibly put in front of patrons, plus an exploratory comparison with model alignment.

1. Choose a Free Model

Connect a no-cost model that supports tool calling: Groq, Google AI Studio, or a fully local Ollama model.

2. Establish the Baseline

See exactly what a bare LLM cannot do: answer questions that need live, local, or current information.

3. Build a Tool-Using Agent

Turn a Python function into a tool with @tool and create the reason–act loop with create_agent.

4. Design Better Tools

Write tool names, docstrings, and arguments that tell the model when and how to use each tool.

5. Connect Scholarly Data

Search Google Scholar, attach DOIs from Crossref, and fall back to OpenAlex in a literature search agent.

6. Add Guardrails

Redact patron PII, require human approval, verify citations, and keep the agent within service scope.

Getting Started: Choose a Free Model

Everything in this module runs on a model that costs nothing. You only need one of the three options below. Tool calling, the model's ability to say "call literature_search with query='digital preservation'", is the core capability an agent needs, and not every free model supports it equally well.

Task 1: Establishing the Baseline: What a Bare LLM Cannot Do

Before building an agent, see clearly what a model without tools cannot do. Learners ask a question whose answer changes every day and cannot be in any training set:

response = model.invoke("What is the weather like today in West Lafayette, Indiana?")
print(response.content)      # refuses, hedges, or invents a plausible number
print(response.tool_calls)   # [] : it has nothing to call yet

Task 2: Turning the Model into an Agent

A tool is an ordinary Python function with two additions that matter enormously: a type-annotated signature and a docstring. The model never sees your code; it sees the tool's name, description, and argument schema.

@tool
def get_weather(location: str) -> str:
    """Get the current weather for a specific city or location.
    Use this whenever the user asks about weather, temperature, or conditions."""
    ...

agent = create_agent(model, tools=[get_weather],
                     system_prompt="You are a helpful assistant for an academic library. ...")

Hands-on Steps

  1. Define get_weather with @tool and inspect its name, description, and schema.
  2. Build the agent with create_agent: one function call turns a model plus tools into a running agent.
  3. Draw the graph: a model node, a tools node, and an edge that loops back (LangGraph runs underneath).
  4. Ask the Task 1 question again and read the step-by-step reasoning trace: model → tool call → tool result → final answer.

Teaching Point for Librarians

Same model, same question, different outcome. The only change is that the model now has somewhere to look. The trace makes the agent's decisions inspectable, which is the starting point for supervising it.

Task 3: Tool Design Clinic

The most common reason a beginner's agent misbehaves is not the model. It is a vague tool description. Learners give an agent two tools that wrap the same function, one described badly and one described well, and watch which one it picks.

❌ Badly described

@tool
def lookup(q: str) -> str:
    """Look something up."""

✅ Well described

@tool
def lookup_course_reserves(course_code: str):
    """Look up the reading list on reserve
    for a specific course. Use this ONLY for
    course reserves. Do not use it for
    general catalog searches.
    Args: course_code, e.g. "CNIT 566"."""

Teaching Point for Librarians

A tool description is to an agent what a scope note is to a cataloger: it says what belongs here, what does not, and what form the input should take. Good descriptions tell the model when to use a tool, what to pass, and when not to use it.

Task 4: A Literature Search Agent with Real Scholarly Data

Learners replace the stub with a real scholarly source. The agent turns a natural-language research question into a search, retrieves evidence from outside the model, and organizes the results with titles, authors, venues, citation counts, and DOIs.

Hands-on Steps

  1. Create a free SerpAPI account and set SERPAPI_API_KEY in the notebook.
  2. Run the helper functions for Google Scholar, Crossref, and OpenAlex.
  3. Wrap them in the literature_search tool and test it directly.
  4. Give the tool to an agent and ask a real research question.

Limitations to Discuss

Every tool call uses one SerpAPI search, and an agent may search several times while refining a query, so the free quota can run out quickly with a group. Crossref matching can fail for theses, preprints, and less formally published works. Use OpenAlex for repeated testing and save Google Scholar for when it is needed.

Task 5: Guardrails for Public Service

An agent that works is not the same as an agent you can put in front of patrons. In LangChain, the layer between "works" and "deployable" is middleware: small, composable policies that wrap every model call and every tool call. The model itself never changes, so the same guardrails work with Gemini, GPT, Claude, or a local model.

Where guardrails run

HookWhen it runsLibrary example
before_agentOnce, before anything elseRefuse out-of-scope requests (medical, legal, investment)

Around tool callsBefore a tool executesPause email_patron for librarian approval
after_agentOnce, before the answer reaches the patronCheck that cited DOIs came from real search results

Four guardrails you build

🔒 PII Redaction

PIIMiddleware removes emails, card numbers, and IP addresses before the request leaves the notebook.

✋ Human Approval

HumanInTheLoopMiddleware pauses before tools that write, send, or spend: emails, holds, record edits.

📚 Citation Grounding

A custom middleware flags any DOI in the answer that never appeared in a tool result.

🚧 Scope Restriction

A custom middleware refuses out-of-scope requests before spending a single token.

Teaching Point for Librarians

Patron privacy is not a feature request; in most institutions it is a legal and professional obligation. Deterministic guardrails (rules, regex, keyword lists) are fast, free, and predictable but miss what they did not anticipate. Model-based guardrails catch subtler cases but add cost and delay.

What LangChain Will Not Guarantee

A rule in a system prompt, such as "If a search returns nothing useful, try ONE broader search," is a request, not a rule. The model usually honors it. "Usually" is fine for a demo and a poor standard for a service, which is why enforceable checks belong in middleware.

Task 6 (Exploratory): Guardrails vs. Model Alignment

A common question: "Is this the same as the safety training AI companies talk about, like RLHF?" It is not. Think of an AI agent as a new staff member at the reference desk: training shapes how they generally behave, but on the job they still follow library policy, verify information, and ask for approval.

Training-Time Alignment (RLHF, DPO)Runtime Guardrails
WhenDuring trainingDuring each interaction
What changesThe model's weightsHow requests and actions are processed
Who controls itTypically model developersApplication operators, including libraries
Library exampleEncourage helpful, honest responsesBlock access to patron records; verify DOIs

Part A: Measuring hallucination with and without guardrails

Learners ask the same eight questions under three conditions and compare the answers side by side.

Questions

5 from the TruthfulQA benchmark, 2 fake citation traps, 1 real citation control

Conditions

No guardrail · Prompt guardrail · Prompt + self-check middleware (@after_model)

Labels

CORRECT ABSTAINED HALLUCINATED

Expect the clearest difference on the fake citations: a model trained to be helpful tends to produce a well-formatted citation when asked for one, and guardrails can catch it. Watch the real citation control too: if a guardrail refuses a real paper, that is over-refusal, the cost of being too cautious.

Part B (optional, T4 GPU): Training a preference with DPO

Learners change a small model's weights with Direct Preference Optimization, a simpler relative of RLHF, using pairs of a preferred answer (chosen) and a rejected one. The whole method fits in one line:

margin = β × [(chosen answer's gain over the original model) − (rejected answer's gain over the original model)]

Then they compare the model's answers to the same eight questions before and after training.

Teaching Point for Librarians

Preference training teaches a model how to behave when it is unsure; it does not give the model knowledge it lacks. When using externally hosted models, libraries usually cannot change training, but they can define instructions, approved sources, access limits, verification steps, and human oversight. Training and runtime controls are complementary, not alternatives.
