What Are Agentic AI and LangChain, and Why Use Them Here?

In this module, you build something closer to a colleague at the reference desk: an AI agent that decides which sources to search, reads what it finds, and knows when to hand a question to a librarian.

Module Goal: Learners build a working prototype of a library reference assistant with LangChain. It searches real scholarly sources, cites only what it found, protects patron privacy, and asks a librarian before taking sensitive actions. Learners then compare these library-controlled safeguards with how AI vendors train their models (RLHF / DPO), so they know what a library can and cannot control.

What Is Agentic AI?

Think of a self-checkout kiosk and a reference librarian. The kiosk does one fixed job the same way every time. The librarian listens to the question, decides which catalog or database to search, checks the results, and refers the patron elsewhere when needed. An LLM application is the kiosk; an LLM agent is closer to the librarian.

Category LLM-based Application LLM-based Agent
DefinitionAn LLM built into a system for one specific purposeA system where the LLM reasons and chooses its own next step
How it worksFixed path: question in, one answer outA loop: think, pick a tool, use it, check the result, repeat
Who decidesThe developer, in advanceThe LLM, at each step
Library exampleTicket classifier (Module 5), article summarizerReference assistant that searches databases, checks citations, and refers patrons

An agent is not a smarter model. It is the same model placed inside a loop with access to tools, and that loop mirrors a reference interview:

Patron's question→ Plan the search→ Search a source→ Read the results→ Enough to answer?→ Answer or search again

Your role shifts from scripting every step to supervising the process, much as a head of reference supervises a service desk.

What Is LangChain?

LangChain is an open-source toolkit for building AI applications and agents. It provides ready-made building blocks for connecting a model to data, tools, and policies, so you do not have to build the agent loop yourself. Three properties matter most for libraries:

Abstraction

Connect a library system, such as a catalog search, to an agent in a few lines of code.

Standardization

Use a free cloud model for a workshop, then switch to a local model that keeps patron data on-site, without rewriting your code.

Chaining

Add library policies, such as privacy rules and staff approval, around an agent without changing the agent itself.

Why LangChain for This Module?

  • Free to try: everything runs on free or local models, so no budget request is needed to experiment.
  • Readable code: a working agent fits in about ten lines, so librarians can read, check, and adapt it.
  • Policies built in: privacy redaction and staff approval are standard components that match library values.
  • Room to grow: the same agents run on LangGraph, which the LangGraph part of Module 6 uses for multi-step library workflows.

Key Terms for Librarians

You will see these terms throughout the notebook and videos. Each one is explained in plain language here.

LLM (Large Language Model)

The AI model that reads and writes text, such as GPT, Gemini, or Llama.

Agent

An LLM placed in a loop where it can choose tools, act, check the results, and decide when to stop.

Tool

Something the agent is allowed to use, such as a catalog search or a scholarly database lookup.

Tool Calling

The model's ability to request a tool with specific inputs instead of answering from memory.

Reasoning Trace

The step-by-step record of what the agent was asked, which tools it used, and what came back.

Guardrail (Middleware)

A check that runs around the agent to enforce a library policy, such as removing patron emails.

API Key

A password-like code that lets your notebook use a model or data service. Keep it private.

Rate Limit

The maximum number of requests a free service allows per minute or per day.

Hallucination

A confident answer that is false, such as a citation to an article that does not exist.

RLHF / DPO

Training methods that use people's preferences between answers to change the model itself.

The Library Agent-Building Workflow

This module follows six steps, from a general-purpose chatbot to a reference assistant you could responsibly offer to patrons, plus an exploratory look at how vendors train their models.

1. Choose a Free Model

Pick a no-cost model that can use tools: a fast cloud option for workshops, or a local model for anything involving patron data.

2. Find What a Chatbot Can't Answer

See where a model alone fails at the desk: today's hours, current holdings, and other live information.

3. Give It a Library Tool

Turn a small piece of code into a tool the agent can use, the same pattern you would use to connect a catalog or hours system.

4. Write Tools Like Scope Notes

Describe each tool so the agent knows when to use it, what to pass, and when not to use it.

5. Connect Scholarly Sources

Search Google Scholar, add DOIs from Crossref, and fall back to OpenAlex, as a librarian would in a research consultation.

6. Apply Library Policies

Protect patron privacy, require staff approval, verify citations, and keep the agent within reference-desk scope.

How to Connect Your Model

  1. Open the Module 6 Colab notebook and sign in with your Google account.
  2. Get a free API key from Groq or Google AI Studio. Ollama needs no key, but it runs on your own computer.
  3. Run the install and import cells at the top of the notebook.
  4. In the Choose a Free Model cell, set PROVIDER to "groq", "google", or "ollama". Run the cell and paste your key into the hidden prompt. Never type a key directly into a cell you might share.
  5. Run the Build the model object cell. If it prints ready, you are connected.
  6. If you later see error 429, you have hit a rate limit. Wait a minute and run the cell again.

Free-tier models and limits change often. Check each provider before running the module with a group.

Per-minute limit (RPM / TPM)

A "speed limit": like a reference desk policy that allows only so many questions per minute so the librarian isn't overwhelmed by a sudden rush.

Daily limit (RPD / TPD)

A "daily allowance": like a daily checkout limit. Once you reach it, you wait until the allowance resets tomorrow.

The notebook uses the weather because it is an unmistakable example; at a library desk, the same gap appears with today's hours, current holdings, and newly published research.

✅ Expected Outcome

A recorded "baseline" answer that refuses, hedges, or guesses, and proof that the model used no tool.

Teaching Point for Librarians

Diagnose first, then choose the tool. Just as you inspect a PDF's text layer before deciding whether OCR is needed, you check what the model cannot know before deciding which library systems to connect it to.

Task 2: Turning the Model into an Agent

About this task: You give the model its first tool and turn it into an agent. A tool is a small piece of code with a clear name and a plain-language description; the model never reads your code, only that name and description. The notebook starts with a simple weather lookup; in a real library, the same pattern connects an agent to your catalog, hours calendar, or room booking system.

🎯 Learning Objectives

  • Turn a piece of code into a tool.
  • Build an agent with one function call.
  • Read a reasoning trace step by step.

🔑 Before You Start

  • Task 1 completed in the same Colab session.

✅ Expected Outcome

A working agent, and a four-step trace in which it calls the weather tool and answers from the result.

Worked Example: Reading the Reasoning Trace

Ask the agent the same question as in Task 1. The trace shows four steps:

1
Question: "What is the weather like today in West Lafayette?"
2
Agent decides to use a tool: it calls get_weather and fills in the location "West Lafayette, Indiana" by itself.
3
Tool result comes back: "clear skies, -2 degrees Celsius, wind 8 km/h". This is practice data, built into the notebook.
4
Final answer: the agent writes a short reply based on that result.
@tool
def get_weather(location: str) -> str:
    """Get the current weather for a specific city or location.
    Use this whenever the user asks about weather, temperature, or conditions."""
    ...

agent = create_agent(model, tools=[get_weather],
                     system_prompt="You are a helpful assistant for an academic library. ...")

Hands-on Steps

  1. Create the get_weather tool and look at the name, description, and inputs the model will see.
  2. Build the agent with create_agent: one function call turns a model plus tools into a running agent.
  3. Draw the agent's diagram: a model step, a tool step, and an arrow that loops back.
  4. Ask the Task 1 question again and read the reasoning trace.

Teaching Point for Librarians

Same model, same question, different outcome: the model now has somewhere to look. And it trusts that source completely, so an agent is only as reliable as the library data you connect it to. The trace shows every decision it made, which is where supervising an agent begins.

❌ Badly Described

@tool
def lookup(q: str) -> str:
    """Look something up."""

No hint about when to use it or what q should be.

✅ Well Described

@tool
def lookup_course_reserves(course_code: str):
    """Look up the reading list on reserve
    for a specific course. Use this ONLY for
    course reserves. Do not use it for
    general catalog searches.
    Args: course_code, e.g. "CNIT 566"."""

Says what it does, when to use it, when not to, and gives an example input.

Worked Example: Which Tool Does the Agent Pick?

Patron Question What to Expect
"What is on reserve for CNIT 566?"The agent picks lookup_course_reserves and passes "CNIT 566".
"Tell me about the history of the printing press."Watch closely: the vague lookup tool may be called for a question it was never meant for, because nothing tells the agent to stay away.

Try it yourself: rewrite the vague tool's description for a real service at your library, such as interlibrary loan status, and run the test again.

Teaching Point for Librarians

A tool description is to an agent what a scope note is to a cataloger: it says what belongs here, what does not, and what form the input should take. If you have written scope notes, you already know how to write good tool descriptions: say when to use a tool, what to pass, and when not to use it.

Task 4: A Literature Search Agent for Reference Services

About this task: You replace the practice tool with real scholarly sources. Like a subject librarian in a research consultation, the agent turns a patron's question into search terms, retrieves evidence from outside the model, and organizes the results with titles, authors, venues, citation counts, and DOIs.

🎯 Learning Objectives

  • Connect an agent to real scholarly sources.
  • Read search results and check their DOIs.
  • Recognize the limits of free search services.

🔑 Before You Start

  • Task 2 completed.
  • A free SerpAPI key (sign in with Google and verify by phone; no credit card).
  • Crossref and OpenAlex need no key.

✅ Expected Outcome

A literature search tool that returns real papers, and an agent answer that cites them with DOIs.

Worked Example: From a Patron's Question to Cited Results

1
Patron asks: "I'm writing a paper on community archives. Can you find recent research on how community archives preserve local history?"
2
Agent plans the search: it turns the question into search terms, for example community archives local history preservation, and calls literature_search.
3
Google Scholar returns papers: each with a title, authors, year, venue, snippet, and citation count.
4
Crossref adds DOIs: titles are matched to Crossref records. A paper without a confident match is marked "DOI not found" rather than guessed.
5
Agent answers: a short list of papers with one-line summaries and DOIs. If results are thin, it may search again with broader terms.
Each result looks like: Title · Authors · Year · Venue · Cited by N · DOI (or "DOI not found")

Try it yourself:

  • Ask a question from your own subject area and compare the agent's search terms with the ones you would choose.
  • Switch the search to OpenAlex while practicing, so you do not use up the SerpAPI quota.
  • Ask for "papers with DOIs only" and check whether every DOI really appears in the search results.

Task 5: Applying Library Policies with Guardrails

About this task: An agent that works is not yet an agent you can offer to patrons. In LangChain, library policies become guardrails: small, reusable checks that run around the agent. The model itself never changes, so the same policies work with whichever model your library chooses.

🎯 Learning Objectives

  • Add privacy, approval, citation, and scope guardrails.
  • Verify what the AI provider actually received.
  • Explain why a prompt instruction is not a policy.

🔑 Before You Start

  • Task 4 completed: the literature search tool is set up in this session.

✅ Expected Outcome

An agent that sends no patron details to the provider, a citation check table, and a polite referral for out-of-scope questions.

When Guardrails Run

When the Check Runs Library Example
Before the agent startsRefer out-of-scope requests (medical, legal, investment) instead of answering
Before and after each model callRemove patron details before they reach the AI provider
Before a tool is usedHold an email to a patron until a librarian approves it
Before the answer reaches the patronCheck that every cited DOI came from a real search result

🔒 Patron Privacy

Removes emails, card numbers, and IP addresses before a patron's request leaves the notebook.

✋ Staff Approval

Pauses before actions that write, send, or spend, such as patron emails, holds, or record edits, until a librarian approves.

📚 Citation Checking

Flags any DOI in the answer that never appeared in a search result.

🚧 Reference-Desk Scope

Refers out-of-scope requests elsewhere before the model is even called.

Worked Examples

1. Privacy. A patron writes: "Could you send the results to j.martinez@purdue.edu? My card number is 5105-1051-0510-5100, and my IP is 128.210.14.7." Here is what the AI provider receives:

2. Citations. A patron asks for "three foundational papers on knowledge graph embeddings, with DOIs." Without a guardrail, the agent may fill in DOIs from memory. With citation checking, a table shows each DOI as FOUND IN SEARCH or UNVERIFIED.

3. Scope. A patron asks for a medical diagnosis. The agent replies with a polite referral before the model is called, so the request costs nothing.

Teaching Point for Librarians

Patron privacy is not a feature request; it is a professional obligation reflected in the ALA Code of Ethics. Rule-based guardrails (patterns, keyword lists) are fast, free, and predictable but miss what they did not anticipate. Model-based guardrails catch subtler cases but add cost and delay.

What LangChain Will Not Guarantee

An instruction such as "If a search returns nothing useful, try ONE broader search" is a request, not a policy. The model usually follows it. "Usually" is fine for a demo and a poor standard for a public service, which is why rules that must always hold belong in guardrails.
